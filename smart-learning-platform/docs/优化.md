# 社区模块性能优化总结

## 1. N+1 查询问题

### 问题

帖子列表查询时，每条帖子单独查用户信息、点赞状态、收藏状态，导致数据库请求数随帖子数线性增长。100 条帖子产生 ~200 次额外 SQL 查询。

```java
// 旧代码：每条帖子循环查 DB
posts.stream().map(post -> {
    User user = userMapper.selectById(post.getUserId());  // 1 次查询
    boolean liked = isLiked(userId, post.getId());        // 1 次查询
    ...
})
```

### 解决方案

**批量加载**：将所有需要的 ID 收集后一次性查询，然后用 Map 组装。

```java
// 批量收集所有作者 ID
Set<Long> authorIds = posts.stream().map(Post::getUserId).collect(toSet());
Map<Long, User> userMap = userMapper.selectBatchIds(authorIds);  // 1 次查询

// 批量查点赞状态
Set<Long> postIds = posts.stream().map(Post::getId).collect(toList());
Set<Long> liked = loadUserLikedTargets(userId, postIds);        // 1 次查询

// 组装
posts.map(p -> toResponse(p, userMap.get(p.getUserId()), liked.contains(p.getId())))
```

**效果**：无论帖子数量多少，固定 3 次 SQL（用户 + 点赞 + 收藏）。

## 2. 点赞/评论计数竞态条件

### 问题

读-改-写模式在高并发下数据不一致：

```java
// 危险：读到旧值，做加法，再写回
post.setLikeCount(post.getLikeCount() + 1);
postMapper.updateById(post);
```

两个请求同时读到 `like_count=5`，都写成 `6`，实际应该是 `7`。

### 解决方案

**原子 SQL 更新**：将计数操作下推到数据库层。

```java
@Update("UPDATE community_post SET like_count = like_count + 1 WHERE id = #{postId}")
int incrementLikeCount(Long postId);

@Update("UPDATE community_post SET like_count = GREATEST(like_count - 1, 0) WHERE id = #{postId}")
int decrementLikeCount(Long postId);
```

## 3. Redis KEYS 命令阻塞

### 问题

`evictPostListCache()` 使用 `redisTemplate.keys(CACHE_PREFIX + "*")`。

Redis 是单线程的，`KEYS` 命令会全库扫描。当缓存 key 变多时，每次发帖/删帖都触发全库扫描，**阻塞整个 Redis 服务器**，影响所有业务。

```java
// 危险：全库扫描
Set<String> keys = redisTemplate.keys("community:posts:page:*");
redisTemplate.delete(keys);
```

### 解决方案

**Redis SET 追踪**：用 Set 结构记录所有缓存 key，删除时精确操作。

```java
// 写缓存时同时记录 key 到 Set
redisTemplate.opsForValue().set(cacheKey, data, TTL, SECONDS);
redisTemplate.opsForSet().add("community:posts:cache-keys", cacheKey);

// 清缓存时从 Set 读取，O(N) 仅扫描缓存 key
private void evictCachedPages() {
    Set<Object> keys = redisTemplate.opsForSet().members("community:posts:cache-keys");
    if (keys != null) {
        redisTemplate.delete(keys.stream().map(Object::toString).collect(toSet()));
        redisTemplate.delete("community:posts:cache-keys");
    }
}
```

**效果**：时间复杂度从 O(全库 key 数) 降为 O(缓存 key 数)。

## 4. MySQL 热度计算索引失效

### 问题

热门排序使用 MySQL 数学公式现场计算，导致全表扫描 + Filesort：

```sql
-- 每行都做 POWER 指数运算，索引完全失效
ORDER BY (like_count * 3 + comment_count * 5)
         / POWER(TIMESTAMPDIFF(HOUR, created_at, NOW()) + 2, 1.5) DESC
```

帖子量上去后数据库 CPU 飙升。

### 解决方案

**Redis ZSet 排行榜**：用 ZSet 维护热度分，查询时走主键索引。

```
维护：
  点赞时 → ZINCRBY community:hot:posts +3  {postId}
  评论时 → ZINCRBY community:hot:posts +5  {postId}

查询：
  ZREVRANGE community:hot:posts 0 19           → Redis O(log N)
  SELECT * FROM community_post WHERE id IN (...) → MySQL 主键索引
```

```java
// 热度分更新（供 InteractionService / CommentService 调用）
public void updateHotScore(Long postId, int likeDelta, int commentDelta) {
    double delta = likeDelta * 3 + commentDelta * 5;
    redisTemplate.opsForZSet().incrementScore("community:hot:posts", postId, delta);
}

// 热门查询走 ZSet
private Page<...> getHotPostsFromZSet(Long subjectId, int page, int size, Long userId) {
    Set<Object> idSet = redisTemplate.opsForZSet()
            .reverseRange(zsetKey, (page-1)*size, page*size-1);
    List<CommunityPost> posts = postMapper.selectBatchIds(toLongList(idSet));
    // 按 ZSet 顺序排列后返回
}
```

## 5. God Class 拆分

### 问题

原始 `CommunityService.java` 超过 500 行，包含帖子 CRUD、评论管理、点赞收藏、缓存、限流、敏感词过滤、DTO 转换等所有逻辑。

### 解决方案

按职责拆分为 4 个类：

| 类 | 职责 |
|---|---|
| `PostService` | 帖子 CRUD、列表缓存、热度分更新、发帖限流 |
| `CommentService` | 评论 CRUD、评论限流 |
| `InteractionService` | 点赞/取消、收藏/取消、收藏列表 |
| `CommunityHelper` | 批量用户查询、点赞/收藏状态加载、DTO 转换、敏感词过滤 |

## 6. 类型安全

### 问题

API 返回 `Map<String, Object>`，无编译期类型检查，前端无法预知字段。

### 解决方案

引入强类型 DTO：

```java
// 旧
ApiResponse<Map<String, Object>>

// 新
ApiResponse<CommunityPostResponse>
ApiResponse<CommentResponse>
ApiResponse<PostDetailResponse>       // { post, comments }
ApiResponse<PostMediaResponse>        // { url, mediaType }
```

## 7. 缓存颗粒度

### 问题

将整页 `Page<CommunityPostResponse>` 序列化为一个大对象存入 Redis。只有一个用户发帖或删帖，`evictPostListCache()` 就把所有页面缓存全清空，命中率极低。

### 解决方案（已在 #3 中实施）

- 仅缓存第一页最新列表（TTL 60s），高频访问收益最大
- 热度榜走 ZSet 不缓存
- 搜索不走缓存
- 删除时用 Set 精确追踪，从 Set 读取后删除，不 flush-all

---

## 总结

| # | 问题 | 根因 | 解决方案 |
|---|---|---|---|
| 1 | N+1 查询 | 循环内单条查询 | 批量加载（selectBatchIds + IN） |
| 2 | 计数竞态 | 读-改-写模式 | 原子 SQL（`SET col = col ± 1`） |
| 3 | KEYS 阻塞 | 全库扫描 | Redis Set 追踪 key |
| 4 | 热度索引失效 | 数学公式现场计算 | Redis ZSet 排行榜 |
| 5 | God Class | 单一类职责过多 | 拆分为 4 个服务类 |
| 6 | Map 返回 | 无类型安全 | 强类型 DTO |
| 7 | 缓存粗粒度 | 全量清空 | Set 精确追踪 + TTL |
